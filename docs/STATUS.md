## ⛔ CRITICAL — HQ Admin has NO login, and now HAS price-editing AND order-cancelling screens

**Read this before running, demoing, tunnelling or deploying the HQ app.**

| | |
|---|---|
| **The risk** | The HQ Admin app (`apps/hey-food-hq`) has no application-layer authentication: its "login" is a `<Link>` to `/dashboard`. **Product / Menu Management (`/menu`) and HQ Orders (`/orders`) have shipped, so anyone who can reach the HQ app's URL can change any master price, any per-outlet price override and any availability for the whole business, read every outlet's orders (customer phones masked) and CANCEL ANY order that is not yet completed — with nothing to stop them and nothing recording who did it.** Categorically worse than the other stand-ins (payment stub, POS device key, notification stubs): those touch one outlet's orders or one customer; this reprices everything. |
| **Today** | **The write paths exist:** the backend's `/admin/*` endpoints (menu: prices and availability; orders: list, detail and **cancel**) — behind that one key. The Dashboard and Outlets screens are still mock data. The API is behind `HQ_ADMIN_KEY`, a shared secret held only by the HQ app's server (header `X-Hq-Admin-Key`; unset → 503, production refuses to start with it set): **a stand-in, not authentication** — it stops a stranger calling the API directly, and does nothing about a person who can open the HQ app, because whoever can load a page there can trigger its server actions. Every HQ page carries a permanent on-screen "NO LOGIN" banner. The localhost bind below was installed *ahead of* the write path on purpose. |
| **Enforced now** | `pnpm --filter hey-food-hq dev` / `start` (`apps/hey-food-hq/scripts/serve.mjs`) bind **127.0.0.1 only** and **refuse to start** if `HQ_BIND_HOST` is anything else, unless `HQ_UNSAFE_NETWORK_BIND=I_UNDERSTAND_THIS_IS_UNSAFE` is also set (exact value; `true` / `yes` / wrong case are refused), in which case it prints a large warning. `-H` / `--hostname` passed to the script is refused. **Verified (real runs):** 9 refusal cases all exit 1 with no listener (no override; override `true`, `yes`, lower case; the LAN address; `::`; a lookalike host `127.0.0.1.evil`; `-H`; `--hostname=`), an unknown mode exits 2; by default the app listens on `127.0.0.1`, answers on `localhost`, and is **unreachable at the machine's LAN address** (connection refused); with the override it listens on `0.0.0.0` and **is reachable at the LAN address**. **Before this, the HQ dev server listened on every interface** (Next's default, `0.0.0.0:3004`) and was reachable from the LAN; it now runs localhost-only. Not run: `next start` (needs a build; same wrapper code path). |
| **What this does NOT do** | It is a seatbelt, not security. It covers only those two scripts: running `next` directly, or a tunnel / port-forward / reverse proxy in front of a localhost bind, defeats it, and it does nothing about anyone with access to the machine. **Only real HQ authentication fixes the risk.** The `HQ_ADMIN_KEY` guard on the admin API is a stand-in too: whoever can use the HQ app effectively holds the key's power. |
| **Rules until real auth exists** | (1) Never port-forward, tunnel, reverse-proxy, deploy, or LAN-bind the HQ app. (2) Never set `HQ_UNSAFE_NETWORK_BIND` on anything shared. (3) Do not treat "it's only on our network" as safe. (4) Real HQ auth (blueprint §6 screen 1; dev spec §2 `POST /auth/staff/login`) is a **launch blocker** for any HQ deployment, not a nice-to-have. Also in the backend README: the banner at the top of the file and the first pre-launch checklist item. |

## Known environment quirks (for future reference)

- **Backend Prisma/tsx commands fail from `pnpm run` in PowerShell — `scripts/with-x64-node.mjs` wipes `PATH`. Root cause verified, workaround below, wrapper deliberately not fixed yet.**
  - **Symptom:** `pnpm run prisma:migrate`, `prisma:generate`, `prisma:seed`, `db:seed:*` (anything whose script is `node scripts/with-x64-node.mjs <bare-command> …`) die with `'prisma' is not recognized as an internal or external command` (or `'tsx' is not recognized…`). `pnpm run dev` / `start` are unaffected — their bare command is `node`, which the wrapper itself supplies.
  - **Cause (measured, not guessed):** in PowerShell the parent env key is `Path` (mixed case). The wrapper does `const env = { ...process.env }` — a plain, case-*sensitive* copy — then ``env.PATH = `${x64NodeDir};${env.PATH ?? ""}` ``. `env.PATH` is `undefined` on that copy, so the child's `PATH` becomes **only** the x64 Node dir (probe: 19 entries direct → 1 entry via the wrapper). That drops pnpm's injected `node_modules/.bin` *and* the whole rest of the system PATH. It likely works in shells where the key is exactly `PATH` (e.g. Git Bash) — which would explain why it worked in earlier sessions — but that part is untested.
  - **Workaround (works; use these):** invoke the tool's JS entrypoint directly under the same wrapper, from `apps/hey-food-backend`:
    - Prisma: `node scripts/with-x64-node.mjs node node_modules/prisma/build/index.js <args>` — e.g. `migrate dev`, `migrate dev --create-only --name x`, `generate`, `migrate reset --force --skip-seed`.
    - Seeds/scripts: `node scripts/with-x64-node.mjs node node_modules/tsx/dist/cli.mjs prisma/seed-placeholder.ts` (or `seed-soup-stall.ts`).
    - **`--skip-seed` on `migrate reset`** — Prisma's built-in seed step shells out to bare `tsx` (same PATH problem) and will fail; run the seed explicitly as above afterwards.
  - **`pnpm` itself isn't on PATH in these shells** — use `corepack pnpm …` (packageManager is pinned to pnpm@9.12.0). Workspace-wide `corepack pnpm -r run typecheck|lint` works fine.
  - **The proper fix (not done — wrapper was out of scope):** read the base PATH case-insensitively *before* spreading, e.g. `const basePath = process.env.PATH ?? ""` (Node's `process.env` proxy is case-insensitive on Windows) and set ``env.PATH = `${x64NodeDir};${basePath}` ``, deleting any differently-cased `Path` key from the copy. One line; then the `prisma:*`/`db:seed:*` scripts work through pnpm again and the workaround above is unnecessary.
- **`prisma generate` (and `migrate dev`/`reset`, which run it) fails with `EPERM … query_engine-windows.dll.node` while a backend dev server is running** — the running server holds the engine DLL. Stop the `with-x64-node … node --watch` backend process tree (`taskkill /PID <wrapper pid> /T /F`; there may be more than one duplicate tree), generate/migrate, then restart with `corepack pnpm run dev` from `apps/hey-food-backend`. The migration itself still applies before the generate step fails, so a failed generate leaves the DB migrated but the client stale.
- **Metro servers left running for days go stale — restart with `--clear` before a device test.** A week-old POS Metro (:8082) failed to bundle with "Unable to resolve module expo-constants" even though the package resolves fine; a fresh server built the identical code with no error, so it was stale server state (`node_modules` had been re-linked under it), not a broken install. Start each app's Metro from its own directory: `corepack pnpm exec expo start --clear` (Customer, :8081) and `corepack pnpm exec expo start --port 8082 --clear` (POS). Device testing also needs `adb reverse` for 8081/8082 (whichever app) and 3000 (backend).
- **A POS Metro started with `CI=1` never picks up file changes.** CI mode disables file watching, so after code changes the phone kept loading the old bundle (this pass it still showed the old "kept on this tablet only" notice). Start it plain (`corepack pnpm exec expo start --port 8082 --clear`) and confirm the bundle contains a new string before testing on a device.
- **On-device testing needs the SDK 51 Expo Go, and the test phone is also used for other things.** The project is on Expo SDK 51; a current Expo Go (SDK 57) is refused by Metro ("The installed version of Expo Go is for SDK 57") — reinstall the SDK 51 build (2.31.x). The phone is also someone's everyday phone: **check the foreground app (`dumpsys activity` → `topResumedActivity`) before every screenshot or tap, only act while it is Expo Go, and never send blind taps.** Fixed-coordinate taps also miss when the layout shifts: the OFFLINE strip and the error banner push the queue down by ~100-150 px, so a tap meant for START can land on the card and open the detail screen.
- **`pnpm run dev` (`node --watch`) restarts the backend on its own mid-request.** Node's watcher treats lazily-loaded `node_modules` files (multer, iconv-lite…) as changes the first time a route needs them, so the server bounced during the first API test (`ECONNRESET`). For testing use `corepack pnpm run start` (same code, no watcher). Also: killing the wrapper PID leaves the `--watch` parent alive, which respawns the server and later hits `EADDRINUSE` — kill every `node … src/main.ts` process (see `Get-CimInstance Win32_Process`), not just the listener.
- **`corepack pnpm run typecheck` / `lint` (Turbo) fail with "Unable to find package manager binary"** — turbo can't resolve pnpm through corepack here. Run the same scripts recursively instead: `corepack pnpm -r --no-bail run typecheck` / `… run lint`.
- **Chrome-driven testing:** coordinate clicks land wrongly (the screenshot frame is not the 1800×961 viewport); click by element ref (`find`/`read_page`) instead.
- **Checking the Customer bundle by hand needs `transform.routerRoot`.** Expo Router only finds this app's routes if the bundle URL carries `&transform.routerRoot=src%2Fapp` (the app keeps its routes in `src/app`, not `app`); without it the request still returns HTTP 200 but bundles an *empty* route tree — no screens, no i18n, nothing — which looks like success. Every screen in every app has been silently rendering in the platform default system font this whole time. Real design-system gap — needs its own follow-up task to actually load Inter, not folded into this pass.
- **hey-food-hq's Tailwind dev server silently drops custom color classes** (`bg-health-*`, etc.) after most file edits, rendering them fully transparent with no error — reproduced repeatedly while building the Outlet List/Detail screens. Classes used only via a shared/extracted component (e.g. `HealthDot.tsx`) seem especially prone to this; a plain `pnpm dev` Fast Refresh does not reliably pick them back up. **Workaround**: kill the dev server, `rm -rf .next`, and restart — confirmed to fix it every time it's been hit so far. ## Future ideas (not in scope)

Captured for later planning only. Nothing here is scheduled, designed, or committed to. Each entry says what it is, why it matters, and what has to exist first. (The larger multi-tenant platform idea has its own document: [docs/future-platform-idea.md](future-platform-idea.md).)

### Automatic sold-out from real inventory counts

- **What:** Replace the Menu Availability screen's manual on/off toggle (dev spec Section 5.3, which writes `OutletProductOverride.is_available`) with availability driven by real stock counts, so an item goes sold-out on its own when it runs out instead of relying on staff to flip it.
- **Why it matters:** the manual toggle only works if someone notices and acts mid-rush. A missed toggle means customers can order, and pay for, food the outlet can no longer make.
- **Depends on:** inventory tracking, which does not exist yet: stock quantities per ingredient/product, decremented on every order (plus a way to restock and correct counts). That is its own prerequisite feature, not a small add-on to the toggle. Ingredient-level options that carry a quantity (e.g. "Fish Balls x2" on the DIY Soup Bowl) would presumably need to decrement stock too, so the decrement is not per product alone.
- **Source:** Eats365 POS competitive research.

### Three-tier staff roles: store / brand / organization

- **What:** A more granular access hierarchy with store, brand, and organization levels.
- **Where we are today:** three roles inside a single business: `hq_admin` (everything), `area_manager` (a defined set of outlets), and `outlet_staff` (one outlet) (blueprint Section 13; `StaffRole` in `packages/shared-types`). The proposal adds scope levels above a single business: brand and organization.
- **Why it matters, and when:** only relevant if Hey Food ever manages multiple brands or franchisees under one platform. It is not needed for the current single-business, single-brand system.
- **Depends on:** the deferred multi-tenant platform idea ([docs/future-platform-idea.md](future-platform-idea.md)), which already anticipates a platform-admin layer above HQ Admin. Brand and organization roles only make sense once `Business` can represent many independent owners.
- **Source:** Eats365 POS competitive research.
